# Lessons Learned

This document captures longer-term learnings to avoid repeating mistakes.

| Lesson | Description |
|--------|-------------|
| Activate Python Virtual Environment First | Before invoking python commands, activate the Python virtual environment to ensure access to all correct packages. Do this by running: `source .venv/bin/activate`. |
| Viewing Parts with ocp_vscode | In order to view a part, the `ocp_vscode` server must first be started in the background by activating the virtual environment (if not already activated) and running `python -m ocp_vscode &`, and then the `show` function must be called in the python code for a part. |
| Checking Port Before Starting OCP Server | Before starting the OCP server, check if port 3939 is already in use. If something is running on port 3939, the server has already been started and does not need to be started again. Only start the server with `python -m ocp_vscode &` if port 3939 is available. |
| Consult Modeling Resources | When building 3D models, especially complex features like channels or grids, consult the `resources/modeling/toc.md` directory for general knowledge and specific techniques (e.g., twist-and-lock channels) to avoid common pitfalls like invalid swept solids. |
| Verify Worktree Branch Before Committing | When a sub-agent works in an isolated git worktree, it MUST verify it is in the correct worktree before committing: check `pwd` (should be the worktree path) and `git rev-parse --abbrev-ref HEAD` (should be the task branch, e.g. `story-001-task-2`) before running `git commit`. During Story001, a sub-agent committed its work to the feature branch (`story/001`) instead of its worktree branch, contaminating the feature branch; recovery required `git reset --hard` plus `git cherry-pick` onto the correct branch. |
| Use the Parent Repo's venv in Git Worktrees | The project's Python virtual environment (`venv/`) is gitignored and therefore absent from git worktrees. Sub-agents working in a worktree must use the parent repo's venv python via its absolute path (e.g. `/home/doug/projects/github/3dmodel/<project-name>/venv/bin/python`) or `source` its `activate` script, rather than creating a new venv in the worktree. |
| Use the worktrees Symlink for Sub-Agent Paths | Sub-agent `workdir` and file paths must use the `worktrees/` symlink (e.g. `worktrees/story-001-task-3`), not the real `.kilo/worktrees/...` path. Paths starting with a dot (`.kilo`) trigger a bug in the tool permissions checker, causing sub-agent tool calls to be rejected. |
| Verify all-pairs part intersection in assemblies | When verifying an assembly, boolean-intersect every part against every *other* part in the assembly, not just part↔connector pairs. Adjacent parts that share an edge can overlap in ways that a pairwise-with-connector gate misses, so include the all-pairs intersection check as a hard gate in any future assembly verification. |
| Avoid Dot-Prefixed Path Tokens in Sub-Agent Prompts | When dispatching a sub-agent task, the prompt must not contain path tokens that start with a dot (e.g. `.kilo/...`): even mentioning them in the prompt text (not just using them as a workdir) caused the dispatch to be aborted twice during Story007 Task 4. Reference such directories by their contents instead (e.g. "the config directory containing `agent/`, `agent-manager.json`, `node_modules/`") and use only the `worktrees/` symlink path form for the worktree. |
| Sub-Agents Must Work Inside Their Designated Worktree | A sub-agent must set its `workdir` to the assigned worktree path for EVERY bash command and file operation, and verify with `pwd` and `git rev-parse --abbrev-ref HEAD` before creating any files. During Story007 Task 3, `code-for-story-implementor` executed in the main workspace instead of the worktree, leaving `.venv` and stray files in the main workspace and completing nothing in the worktree; escalation to `big-code-for-story-implementor` (which worked in the worktree) succeeded. |
| Writing Agents Can Hit the Operation Limit Mid-Task | The operation limit is not unique to `small-code-for-story-implementor`. During Story008 Task 3, `technical-writer-for-story-implementor` completed and verified all edits but hit its operation limit before committing, leaving verified-but-uncommitted work in the worktree. Instead of re-dispatching a fresh writer to redo the work, the story-implementor verified the full `git diff` end-to-end (read-only) and committed it in the worktree as a coordination checkpoint. |
| Screw dimensions live in resources/modeling/screws.md | When modeling holes for screws (clearance holes, pilot holes, countersinks, counterbores), consult `resources/modeling/screws.md` for the dimension tables: gauge-to-diameter, clearance/pilot hole sizes, and head diameter/height. It also documents the build123d `CounterSinkHole` and `CounterBoreHole` operations. This is the place to look for screw dimensions. |
| Vertical mill jig mounting reference lives in resources/modeling/vertical_mill_jigs.md | When a vertical mill jig is being created, consult `resources/modeling/vertical_mill_jigs.md`. It documents the standardized M5 mounting screw, the countersunk hole feature and base thickness, and the bed's mounting-hole pattern (7 × 5 grid with the lower-left hole missing). This is the place to look if a vertical mill jig is being created. |
